# 通用评审基础框架

> **适用范围**: 代码评审（PR）、设计文档评审
> **定位**: 定义通用评审原则、缺陷等级、结论判定、输出规范。各角色评审时引用本文件，仅声明差异化检查项（见 `_common/code-review-checklist.md`）。

---

## 1 通用评审原则

1. **零遗漏原则**：MUST 级检查项逐项核查，不得遗漏；未核查项需说明原因
2. **红线否决原则**：P0 ≥ 1 或 P1 ≥ 2 → 直接不通过
3. **可落地原则**：所有问题定位到具体文件/行号/章节，禁止泛泛而谈，必须给出整改方向
4. **多角色视角**：同时从用户/产品、技术、测试三个视角评审
5. **内容优先原则**：功能/内容遗漏的优先级高于格式瑕疵
6. **Upstream-First 原则**：上游依据（issue、设计文档、ADR、API 契约）是评审基准；先理解上游再审查实现，而非只查内部一致性
7. **评审独立性原则**：评审不得由产出者本人执行（编码者不评审自己的 PR；设计者不终审自己的方案）；评审前不预设作者结论

### 1.1 举证义务（P0/P1 三要素）

每条 P0/P1 缺陷必须包含，缺一降级为 P2 或撤销：

1. **原文引用**：文件+行号 / 章节号 + 原文片段（≤ 50 字）
2. **检查项链接**：对应检查清单条目（如 code-review-checklist §6.1）
3. **下游影响**：一句话说明不整改的具体后果

### 1.2 评审自满防控

- 长清单下评审者天然宽松倾向：首轮"零缺陷通过"必须额外抽查 2-3 个高风险区域反向核验
- 评审者不得自我终止评审循环；是否放行由协调者/用户决定
- 评审结论必须附独立性声明（见 §4）

## 2 缺陷等级定义

| 等级 | 代号 | 定义 | 整改要求 |
|------|:----:|------|---------|
| 致命 | P0 | 安全漏洞、架构缺陷、必然返工的核心问题 | 必须修复，阻塞合并/通过 |
| 严重 | P1 | 严重影响质量，大概率导致理解偏差或返工 | 必须修复或给出充分理由 |
| 一般 | P2 | 不影响核心落地，降低协作效率或存在细节风险 | 建议修复 |
| 建议 | P3 | 规范性、可读性改进 | 可选采纳 |

## 3 评审结论判定

| 条件 | 结论 |
|------|------|
| P0 = 0 且 P1 = 0 且 P2 ≤ 4 | ✅ 通过 |
| P0 = 0 且 P1 ≤ 1 且 P2 ≤ 6 | ⚠️ 有条件通过（整改后再审） |
| P0 ≥ 1，或 P1 ≥ 2，或 P2 ≥ 7 | ❌ 不通过 |

- 分数与缺陷冲突时，以缺陷判定为准
- 评审轮次上限 3 轮；超过升级人工决策

## 4 评审输出结构

评审报告结构见 `_common/agent-templates.md` §10。强制要求：

- **首段独立性声明**：声明本次评审独立完成 MUST 全量核查
- **缺陷统计**与**结论**必须明确
- 每条 P0/P1 按三要素举证（§1.1）
- 输出语言专业、直白；禁止"描述模糊""架构不合理"等无指向表述

## 5 特殊约束规则

1. 上游一致性核查义务：同时提供实现与设计文档时，必须核对一致性
2. 语义对齐（D0）优先于格式规范检查；发现 P0 时格式检查可从简
3. 不完整输入处理：输入仅为片段时，先声明评审范围再评审，并提示缺失风险
4. 置信度标注不作为放行依据：🟢 项的核查力度不得低于 🔴 项（见 `_common/confidence-marking.md`）
